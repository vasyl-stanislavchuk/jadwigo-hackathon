Jadwigo is one web app, one API and an AI engine, and all of it is serverless. This page shows it
at 2 zoom levels: first who uses it and what it leans on, then the containers a request moves
through. The pages after it zoom in further.

## Context

<Diagram name="context" caption="4 kinds of user, 1 system, 3 things it leans on." />

A child plays a lesson from a link, with no account. A parent signs in, chats with Jadwigo about
what their child needs, and gives the lesson it builds. A parent's own AI app, such as a chat
assistant, can reach the same data through a remote MCP server once the parent says yes. A lesson
author or an agent searches the question bank to build lessons.

Jadwigo leans on 3 things. Supabase holds the records and signs parents in. Meta Muse is the model
the AI engine calls, 1 call per step. The question bank holds the credited question sets that
lessons are made from, and Jadwigo searches it and reads each question's body.

## Containers

<Diagram name="containers" caption="Runtime path. The runner, in blue, does the AI's work." />

- **Web app** at `app.jadwigo.pl`: the lesson player and the parent's chat. It calls the API only
  through the shared typed client, on the same origin, so it needs no CORS.
- **API Gateway** throttles every route. On a parent route it checks the parent's Supabase token
  before the Lambda runs.
- **API**: one Lambda holds every route. It parses each request against its schema, runs
  `authorize()` first and runs the whole request in one database transaction. It also serves the
  remote MCP server at `/api/mcp`.
- **Runner**: a 2nd Lambda that runs the AI engine. The API writes a chat turn's step into a queue
  in Postgres, in the same transaction as the message, then pokes the runner. The API never waits
  for the model. See [AI engine](/architecture/ai-engine/).
- **Uploads and the converter**: a parent's photo goes straight from the browser to a private S3
  bucket, under the family's own prefix. A PDF, DOCX or HEIC goes to the converter Lambda, which
  writes 1 JPEG per page.
- **Postgres**: every record. Row-level security keeps each family's rows to that family.
- **Question bank**: the API searches it and reads a question's body from it. The runner's bank
  verbs go through those same API routes, so nothing else reads the bank directly.
- **Meta Muse**: the model API. Only the runner calls it, and every call is capped and logged.

A merge to `main` deploys nothing. Vasyl deploys each part by hand, and applies the Terraform
by hand too.

## Serverless

No server of Jadwigo's own runs between requests. The compute is 5 Lambda functions, the web app
and the sites are static files behind CloudFront, and Supabase runs Postgres and sign-in as a
managed service. Lambda bills per request, so a quiet hour costs next to nothing, and a busy one
scales without anyone adding a machine.

- **One function per kind of work.** The API answers requests, and the runner does the AI's
  steps. The converter turns a PDF, DOCX or HEIC into pages, print renders a lesson's PDF, and
  bank search finds questions.
- **Slow work leaves the request.** The API writes a chat turn's step to a queue in Postgres, in
  the same transaction as the message, and pokes the runner. A schedule pokes it once a minute
  too, so no step waits on a lost poke.
- **No machine to patch.** A deploy uploads new function code and static files, and Terraform
  holds the rest.
