This page is for anyone connecting an AI agent to `jw mcp serve`, Jadwigo's MCP server: how to
register it, how an agent drafts a lesson with it, and every tool it gives.

The server speaks MCP on stdio. An agent uses it to search the question bank and to draft a lesson
for a parent. Each tool calls the same function as a `jw` command, so a tool's JSON is that
command's `--json` output. A call that fails comes back as a tool error. Its text is the error and
a hint.

## Register the server

The server runs from a checkout of the repo through `uv`. It finds the bank's URL and token in
`~/.config/jadwigo-bank/bank.env`. `JADWIGO_BANK_DIR` can sit in that file too, in place of the
`env` entry. Replace the 3 paths below with your own.

### Claude Code

Put the name before the `-e` flags, and give each variable its own `-e`. The flag takes every
value up to `--`, so a name after it is read as a variable.

```sh
claude mcp add --scope user --transport stdio jadwigo \
  -e JADWIGO_BANK_DIR=/path/to/jadwigo-bank \
  -e JW_KHAN_CONVERTED=/path/to/converted-pl.json \
  -- uv --directory /path/to/jadwigo/apps/cli run jw mcp serve
```

`claude mcp list` then shows `jadwigo`. `claude mcp remove jadwigo -s user` removes it.

Or check it in for a project as `.mcp.json`:

```json
{
  "mcpServers": {
    "jadwigo": {
      "type": "stdio",
      "command": "uv",
      "args": ["--directory", "/path/to/jadwigo/apps/cli", "run", "jw", "mcp", "serve"],
      "env": {
        "JADWIGO_BANK_DIR": "/path/to/jadwigo-bank",
        "JW_KHAN_CONVERTED": "/path/to/converted-pl.json"
      }
    }
  }
}
```

### Codex

```sh
codex mcp add jadwigo \
  --env JADWIGO_BANK_DIR=/path/to/jadwigo-bank \
  -- uv --directory /path/to/jadwigo/apps/cli run jw mcp serve
```

### Muse Code :badge[Unconfirmed]{variant=caution}

Muse has no `mcp add` command. A stdio server is an entry under `mcpServers` in
`~/.config/muse/settings.json`, whose top level also needs `"schema_version": 1` (line 2 below).
The entry's field names, on lines 5 to 8, are not confirmed yet: Muse does not warn on a wrong
one. Lines 6 to 8, folded, are the same `command`, `args` and `env` as in `.mcp.json` above.

```json showLineNumbers collapse={6-8}
{
  "schema_version": 1,
  "mcpServers": {
    "jadwigo": {
      "transport": "stdio",
      "command": "uv",
      "args": ["--directory", "/path/to/jadwigo/apps/cli", "run", "jw", "mcp", "serve"],
      "env": { "JADWIGO_BANK_DIR": "/path/to/jadwigo-bank" }
    }
  }
}
```

## Draft a lesson

A lesson from the bank copies each question whole, its help included, and plays as copied. The
agent writes only what the bank does not have.

1. **Draft.** Call [`lesson_draft`](/mcp/lesson_draft/) with the parent's request. Pass every name
   the family uses in `names`. The tool replaces them before anything leaves the machine. Pass
   the `topic` in a few words, with no count, grade or name (`mnożenie`): the bank searches it.
   The draft stays on the server's machine under a `draft_id`, and a short view of it comes back.
   The draft is on disk from this first call (see below).
2. **Write what is missing.** Each question's `you_write` lists it: the `twin` when the bank has
   no sibling item to copy as one (`twin_source` names the bank's), `boost_by_mistake` for the
   classes in `cards_to_write`, and any rung the copy leaves empty. Write it in the lesson's
   language. Change a copied part only when the parent asks, as a change in `changes`.
3. **Check.** Call [`lesson_check`](/mcp/lesson_check/) with the `draft_id` and your words by step
   id. Send only the steps you write for: a step left out keeps what the draft holds. Pass
   `names` again: every word you send has them replaced. Fix each error in its `findings` by step
   id, and check again until it answers `ok` with a card. The card is short: plain text, no
   rungs. Pass `full: true` for each rung, and `verbose: true` for each warning.
4. **Change one step.** Read it with [`lesson_show`](/mcp/lesson_show/) and patch it with
   [`lesson_edit`](/mcp/lesson_edit/). The patch is a JSON merge patch on the step: an object
   merges, `null` removes a part, anything else replaces it. A change to the bank's copy (`say`,
   `data`, `key`, `hints`, `worked`) needs a `why`, and it is recorded in `based_on.changes`. The
   answer is that step's findings and card. A later `lesson_check` keeps the edit unless it is
   sent words for that step.
5. **Publish, then play.** Once a check answers `ok`, call [`lesson_publish`](/mcp/lesson_publish/)
   with the `draft_id`, without asking. It imports the lesson into the local database `make dev`
   serves. Then it checks that the api answers, that a preview attempt starts with every question,
   and that the play page answers. It returns the absolute `play_url` for the parent. It publishes
   only locally: for jadwigo-dev it refuses and names the owner's command, and the live app is
   never published from here.

### Lesson-ready questions

A draft copies only a lesson-ready question: the bank checked that it compiles, that its key
grades its own answer, that every picture loads and that the page draws it without an error. Each
item the draft did not use is in `left_out` with a reason about the item, never the child:

- `renders wrong: <rule>`: a check failed, such as `render-raw-tex` or `key-grades`.
- `not checked`: the bank has no verdict on it yet, so it waits.
- `flagged: <reason>`: a person pulled it.
- The converter's own reason: the bank cannot make it yet.
- `no item is lesson-ready in <lang>`: a whole set has none in the lesson's language.

[`question_gaps`](/mcp/question_gaps/) counts such a set as a gap, and its reason goes on to name
the cause most of the set's items share and the bead fixing it, as in `no item is lesson-ready in
pl; most: a picture was not pulled, 12 of 12 items (<bead>)`.
[`question_item`](/mcp/question_item/) answers with the same reason as an error. Fixing a refused
item happens at its source, on the command line: `jw question readiness` counts, per language,
what is ready, waiting and refused, by cause and with each cause's bead; `jw question refusals`
lists the shapes, the converter's refusals among them; and `jw question flag` pulls one item.

### The draft on disk

Both lesson tools write the draft into one directory, `JADWIGO_DRAFTS_DIR`, read from the server's
environment only, with `~` expanded. It defaults to `~/.local/state/jadwigo/drafts` on the server's
machine, and only its owner can read it. A `title` or `reasoning` you pass to `lesson_check` has
the `names` you pass replaced before it is written. Each call writes 2 files there before it
returns:

- `<draft_id>.json` is the lesson file as far as it goes. `lesson_draft` writes the copy, with its
  empty rungs. Every `lesson_check` call rewrites it with your words, even when it refuses them.
  The result names it `draft_path`.
- `<draft_id>.check.json` is the check beside it: `ok`, `findings`, `mistake_classes` by step id,
  and `checked_at`.

`lesson_edit` rewrites both too. The lesson builder's page writes a third file when it draws the
draft, `<draft_id>.render.json`: what it found wrong on the page. `lesson_check`, `lesson_edit`
and `lesson_show` return its findings as `render`, with `rendered_at`, and `stale` when the page
drew an older version. `render` is null when no page has drawn the draft. `lesson_publish` writes
`<draft_id>.publish.json`, readable by its owner only: the same record it returns, with the
`play_url` and what was verified.

A finding has a `step_id`, a `path` into the lesson file, a `level` (`error` or `warn`), a `rule`,
its `text` and a `fix`. `ok` is true while no finding is an error. The live lesson builder reads
these files, so a draft renders while you write it.
