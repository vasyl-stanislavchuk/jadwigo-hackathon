Jadwigo has 2 MCP servers. This page is for anyone connecting an AI agent to either of them: how
to register each one, how an agent drafts a lesson, and every tool the local server gives.

- **`jw mcp serve`** runs on your own machine, on stdio, for a lesson author. It searches the
  question bank and drafts a lesson, and it publishes only to the local app.
- **`https://app.jadwigo.pl/api/mcp`** is the remote server, for a parent's own AI app. The app
  signs in by OAuth 2.1 and acts as that parent, inside their family's data.

The table under "Every server" puts the 2 side by side.

## Local server

`jw mcp serve` speaks MCP on stdio. Each tool calls the same function as a `jw` command, so a
tool's JSON is that command's `--json` output. A call that fails comes back as a tool error. Its
text is the error and a hint.

### Register the server

The server runs from a checkout of the repo through `uv`. It finds the bank's URL and token in
`~/.config/jadwigo-bank/bank.env`. `JADWIGO_BANK_DIR` can sit in that file too, in place of the
`env` entry. Replace the 3 paths below with your own.

#### Claude Code

Put the name before the `-e` flags, and give each variable its own `-e`. The flag takes every
value up to `--`, so a name after it is read as a variable.

```sh
claude mcp add --scope user --transport stdio jadwigo \
  -e JADWIGO_BANK_DIR=/path/to/jadwigo-bank \
  -e JW_KHAN_CONVERTED=/path/to/converted-pl.json \
  -- uv --directory /path/to/jadwigo/apps/cli run jw mcp serve
```

`claude mcp list` then shows `jadwigo`. `claude mcp remove jadwigo -s user` removes it.

Or check it in for a project as `.mcp.json`:

```json
{
  "mcpServers": {
    "jadwigo": {
      "type": "stdio",
      "command": "uv",
      "args": ["--directory", "/path/to/jadwigo/apps/cli", "run", "jw", "mcp", "serve"],
      "env": {
        "JADWIGO_BANK_DIR": "/path/to/jadwigo-bank",
        "JW_KHAN_CONVERTED": "/path/to/converted-pl.json"
      }
    }
  }
}
```

#### Codex

```sh
codex mcp add jadwigo \
  --env JADWIGO_BANK_DIR=/path/to/jadwigo-bank \
  -- uv --directory /path/to/jadwigo/apps/cli run jw mcp serve
```

### Draft a lesson

A lesson from the bank copies each question whole, its help included, and plays as copied. The
agent writes only what the bank does not have.

1. **Draft.** Call [`lesson_draft`](/mcp/lesson_draft/) with the parent's request. Pass every name
   the family uses in `names`. The tool replaces them before anything leaves the machine. Pass
   the `topic` in a few words, with no count, grade or name (`mnożenie`): the bank searches it.
   The draft stays on the server's machine under a `draft_id`, and a short view of it comes back.
2. **Write what is missing.** Each question's `you_write` lists it: the `twin` when the bank has
   no sibling item to copy as one (`twin_source` names the bank's), `boost_by_mistake` for the
   classes in `cards_to_write`, and any rung the copy leaves empty. Write it in the lesson's
   language. Change a copied part only when the parent asks, as a change in `changes`.
3. **Check.** Call [`lesson_check`](/mcp/lesson_check/) with the `draft_id` and your words by step
   id. Send only the steps you write for: a step left out keeps what the draft holds. `names` is
   required on every `lesson_check` and `lesson_edit` call: the same list you gave
   `lesson_draft`, or `[]` when the family named nobody. Every word you send has them replaced.
   Fix each error in its `findings` by step id, and check again until it answers `ok` with a
   card. The card is short: plain text, no rungs. Pass `full: true` for each rung, and
   `verbose: true` for each warning.
4. **Change one step.** Read it with [`lesson_show`](/mcp/lesson_show/) and patch it with
   [`lesson_edit`](/mcp/lesson_edit/), with the same `names`. The patch is a JSON merge patch on
   the step: an object merges, `null` removes a part, anything else replaces it. A change to the
   bank's copy (`say`, `data`, `key`, `hints`, `worked`) needs a `why`, and it is recorded in
   `based_on.changes`. The answer is that step's findings and card. A later `lesson_check` keeps
   the edit, less any part that check's words for that step set. To put the steps in another
   order, easy to harder, call [`lesson_move`](/mcp/lesson_move/) with a step and `before` or
   `after` another. Every later check keeps the order. To take a step out, call
   [`lesson_drop`](/mcp/lesson_drop/). A draft keeps at least one step.
5. **Publish, then play.** Once a check answers `ok`, call [`lesson_publish`](/mcp/lesson_publish/)
   with the `draft_id`, without asking. It imports the lesson into the local database `make dev`
   serves. Then it checks that the api answers, that a preview attempt starts with every question,
   and that the play page answers. It returns the absolute `play_url` for the parent. It publishes
   only locally. For the dev environment it refuses and names the command to run instead, and the
   live app is never published from here.

#### Lesson-ready questions

A draft copies only a lesson-ready question: the bank checked that it compiles, that its key
grades its own answer, that every picture loads and that the page draws it without an error. Each
item the draft did not use is in `left_out` with a reason about the item, never the child:

- `renders wrong: <rule>`: a check failed, such as `render-raw-tex` or `key-grades`.
- `not checked`: the bank has no verdict on it yet, so it waits.
- `flagged: <reason>`: a person pulled it.
- The converter's own reason: the bank cannot make it yet.
- `no item is lesson-ready in <lang>`: a whole set has none in the lesson's language.

[`question_gaps`](/mcp/question_gaps/) counts such a set as a gap, and its reason names the cause
most of the set's items share, as in `no item is lesson-ready in pl; most: a picture was not
pulled, 12 of 12 items`. [`question_item`](/mcp/question_item/) answers with the same reason as an
error. A refused item is fixed at its source, on the command line. `jw question readiness` counts
what is ready, waiting and refused in each language, by cause. `jw question refusals` lists the
shapes, the converter's refusals among them. `jw question flag` pulls one item.

## Remote server

`https://app.jadwigo.pl/api/mcp` is how a parent's own AI app, such as claude.ai, ChatGPT or Muse,
makes lessons in Jadwigo. It's on `main` and not yet live on prod.
[Connect your AI](/features/connect-your-ai/) walks a parent through it.

- **Transport.** Streamable HTTP, stateless, with JSON replies and no server-sent events. Only
  `POST` is served, and a `GET` or `DELETE` is `405`. A request body is at most 256 KiB, and a
  batch of messages is refused.
- **Sign-in.** OAuth 2.1, with Supabase Auth as the authorization server. A call without a valid
  token is `401`, and its `WWW-Authenticate` header names the protected-resource metadata at
  `/.well-known/oauth-protected-resource`. The client follows it, the parent signs in and approves
  the app on the consent page, and the client gets a token. [Authentication](/guides/authentication/)
  has the details.
- **Rights.** The token carries the same rights as the parent's own token in the web app. The AI
  reads only that parent's family, plus the question bank.
- **Tools.** The read tools cover everything the parent can read in the app: `me`, the children's
  attempts, skills, goals and reports, the conversations and their runs. `question_search`,
  `question_set` and `question_show` read the bank. The lesson tools are `lesson_draft`,
  `lesson_check`, `lesson_show`, `lesson_edit` and `lesson_publish`. Here `lesson_publish`
  publishes for real, for 1 named child, and answers that child's play link.

## Every server

| | `jw mcp serve` | `/api/mcp` |
| --- | --- | --- |
| Who uses it | A lesson author, on their own machine | A parent's own AI app |
| Transport | stdio | Streamable HTTP, JSON replies |
| Sign-in | None: the bank's token in a local file | OAuth 2.1, the parent's own account |
| Reads | The question bank | The parent's family and the question bank |
| Publishes | To the local app only | To the app it serves, for 1 named child |
