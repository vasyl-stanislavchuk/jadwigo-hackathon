# dl-z5ja: wave 1 plan, the Jadwigo AI engine foundation

Epic `dl-z5ja`. Wave label `wave:dl-z5ja-1`. A parent's chat on the left becomes a lesson on the
right, PostHog's way. Wave 1 builds the engine's primitives and proves the whole chat → lesson loop
locally, with no network, no migration, no route and no paid call:
1. A parent's message lands in `run_inbox`.
2. `runStep` drives a fake Muse through the lesson verbs.
3. Every effect is a `run_event` in the in-memory store.
4. The dev page `/playground/chat` subscribes, fetches, dedupes and folds the log into 2 panes.

What wave 1 writes is final above the adapters. Wave 2 only swaps in real adapters: Postgres, pgmq,
Realtime, the real Muse client and the step consumer's host.

Read first:
- `docs/research/posthog-ai-runtime.md` (the architecture);
- `docs/research/ai-chat-engine.md` (the Supabase-native design);
- `docs/research/posthog-ai-production.md` (what PostHog fixed in production, and the copy table this plan follows).

## Decisions in force

  - "Let's adopt Posthog patterns as much as possible";
  - Supabase to the max, with Supabase Queues as the queue;
  - the hosted agent runs on Muse models;
  - the builder becomes the parent's editor;
  - stay serverless "to most extent";

- **The owner, 2026-10-31, in this plan's session:**

  - Scheduled AI workflows (digesting, analysis, dreaming, report prep) are coming, but "not in
    foundation. focus on engine primitives for now". The first and only workflow in wave 1 is
    chat → lesson.
- **`jadwigo-ai-workflows/decisions/2026-10-31-a-report-runs-only-when-the-parent-asks-for-it-never-on-a-schedu`.**
  Nothing in this wave schedules a run. Which workflows may run unattended is a separate owner
  question (`dl-hin8.14`).
- **`jadwigo-ai-workflows/decisions/2026-10-31-a-session-may-propose-notes-for-a-learner-s-record-at-its-end-an`.**
  The engine never writes a learner's record in wave 1.
- **`david-learns/decisions/2026-10-24-every-ai-workflow-in-the-jadwigo-service-runs-on-meta-s-api`.**
  The real client is the Muse API (`/v1/responses`) with function tools. Real learner data never
  goes into a prompt (`AGENTS.md`). Since 2026-11-01 it does, on a tier that does not train on it,
  names included (`jadwigo-hackathon/notes/2026-11-01-learner-data-reaches-the-model-by-design-for-the-parent-s-own-re`).

A lane that needs a decision these don't give stops and tells the lead. A question only the owner
can answer goes to the owner.

## Lead decisions

1. **Layers.** The package graph:

   ```
   contracts ─► core ─► store ─► lesson-import ─► jadwigo-ai ─► apps/web (dev plugin)
   ```

   - `packages/jadwigo-ai` is new. It imports `contracts`, `core`, `store` and `lesson-import`
     (for `check.ts` findings and `parseLessonFile`).
   - `core` stays pure and imports `contracts` only. No package imports `jadwigo-ai`.
   - Step 0 adds:
     - the package's row to the `AGENTS.md` layout table;
     - its own `AGENTS.md`;
     - a `"//"` line for each dependency.
2. **Contracts on a subpath until the migration.** `packages/contracts/src/run.ts` is exported as
   `@jadwigo/contracts/run`, **not** from `src/index.ts`.
   - Everything `index.ts` exports gets a JSON Schema snapshot, and a snapshot change is a
     one-way door.
   - `naming.test.ts` matches `RECORDS` against the migrations.
   - So the run records join `index.ts`, `RECORDS`, `ID_SCHEMAS` and the snapshots in the
     `dl-z5ja.7` migration PR, one one-way door together.
   - Step 0 reserves the prefixes `cnv_` and `run_` in `ID_PREFIXES` (a constant, no snapshot) and
     exports `prefixedId` for `run.ts`.
   - It also extends `naming.test.ts` to run its refused-word check over `run.ts`'s fields:
     `step`, `session`, `task` and `item` are refused, and names follow `RULES.md`.
   - `GLOSSARY.md` gains conversation, run, run event and run inbox.
3. **The records** (`run.ts`), each with `pod_id`:
   - **`Conversation`:** `id` (`cnv_`), `pod_id`, `created_by`, `title`, `created_at`.
   - **`Run`:** one per turn.
     - Identity: `id` (`run_`), `pod_id`, `created_by`, `conversation_id` (nullable, so an
       unattended run is possible later), `workflow` (`jadwigo-lesson-compose` only in wave 1),
       `resumes_run_id`.
     - State: `status` (`queued | in_progress | awaiting_input | completed | failed | cancelled`),
       `attempt`, `cancel_requested_at`.
     - **`idle_deadline_at`:** 10 min idle while a turn is open, pushed at most every 30 s.
     - **`max_deadline_at`:** a hard wall clock that activity never moves.
     - Cost: `cap_usd`, `spent_usd`.
     - Times: `created_at`, `completed_at`.
     - These are 2 deadlines, never one. PostHog learned it twice (`4f9d39c016e`, `57c128deeb7`).
   - **`RunEvent`:** `{run_id, seq, event_id, type, payload, created_at}`, a discriminated union on
     `type`:
     - `message` (the parent's or the agent's words), with optional `attachments` as storage
       references, never bytes. These are for the homework epic `dl-z5ja.11`, whose
       photo-to-lesson step runs on this engine;
     - `model_response` (Muse's `response_id`, `call_no`, usage, USD);
     - `tool_call` (`call_id`, verb, input) and `tool_result` (`call_id`, output or error);
     - `lesson_revision` (`revision`, the whole lesson file as JSON);
     - `approval_request` and `approval_resolved`;
     - `status`, `usage`, `budget_steer`, `turn_complete`, `error`.
   - **`RunInbox`:** `{run_id, pod_id, event_id (unique), kind: message | steer | approval | cancel, payload, status: pending | delivered, created_at}`.
   - **`RunStepInput` / `RunStepOutput`:**

     ```
     runStep({run_id, attempt}, deps) →
       {outcome: continue | awaiting_input | turn_complete | cancelled | failed, events: n}
     ```
4. **The lesson pane is a revision, not a patch.** Verbs take a JSON merge patch, as
   `lesson_edit` does today. The log stores `lesson_revision`, the whole file after the edit.
   - The fold keeps the highest `revision`, which is safe under duplicates and replays.
   - A lesson file is a few kB.
   - Contracts treat the file as opaque JSON. `lesson-import` parses it at both edges: the verb
     before it writes, the page with `readDraft`.
5. **Ids and sequence.**
   - `seq` is per run, gapless, `max + 1`, assigned by the store inside `appendRunEvents`.
   - `event_id` is deterministic: uuid v5 of `(run_id, attempt, call_no, item_index)` for model
     output, and Muse's `call_id` for tools.
   - The store ignores an `event_id` it already holds, so a replayed write is a no-op.
   - `seq` is the cursor. `event_id` is the dedupe key. They are never merged
     (`posthog-ai-runtime.md` section 3).
6. **A redelivered step never pays twice or writes twice** (steward gap 1, PR #391). Before calling
   Muse, `runStep` reads the log:
   - A `model_response` for this `call_no` → reuse it.
   - A `tool_call` whose `tool_result` exists → skip the tool.
   - A `tool_call` with no result → run the verb again. Verbs are idempotent by `call_id`.
   - `updateRun` compares and sets on `attempt`. A step holding a stale `attempt` writes nothing
     and ends. This is PostHog's `generation` fence (`c54766909b8`).
7. **Authorization** (steward gap 2).
   - `authorizeRun(store, run_id)` returns `{pod, created_by, run}`, as `apps/api`'s
     `authorize()` does for attempts.
   - Every verb receives a `VerbContext {pod, created_by, run_id}` built from the run row. **No
     verb takes a pod, a learner or an owner from the model's arguments.**
   - Store calls are pod-scoped as they are today.
   - The wave-2 stance: the step consumer connects as a new `jadwigo_runner` role that owns no
     table, under forced RLS, with `app.pod_id` set per unit like `jadwigo_api` (the
     `dl-z5ja.7` migration).
8. **Turn control.**
   - A message during a turn becomes a `run_inbox` row, delivered in order at the next step and
     never lost (`07e5926b92a`, `84ebde9e18f`). A steer joins the next step's context.
   - Cancel sets `cancel_requested_at`, checked before each Muse call and each verb.
   - A late event after `turn_complete` never reopens the turn (`fb0435a3341`).
   - Wave 1 has no verb that needs approval: `lesson_publish` is out. The approval events exist so
     the fold and the page handle them.
9. **Cost.**
   - `budgetGuard(spent_usd, cap_usd)` runs before every Muse call: `none`, `steer` at 50%
     ("finish the lesson with what you have"), `stop` at 90%.
   - A `spent_usd` that can't be read refuses the call. As PostHog puts it, "An unknown balance is
     no licence to spend" (`ff23c1ce7af`).
   - The steer is an event the page shows. PostHog never shows it.
10. **Adapters are interfaces in `jadwigo-ai`.** Each has a fake or in-memory version in wave 1:
    - **`MuseClient`** copies `jw.muse.ask`:
      - a guarded prompt, a `tag`, a budget check;
      - a stable `prompt_cache_key` per workflow;
      - a ledger row per call, carrying the `run_id`.

      `FakeMuse` lives in `src/testing/` and replays scripted responses with tool calls.
    - **`RunQueue`** has `send`, `read(vt)`, `archive` and dead-letter after `read_ct > 3`, shaped
      like pgmq. Wave 1 uses `InMemoryRunQueue`.
    - **`BankPort`** serves `question_search` and the sources for `lesson_draft`. Wave 1 uses a
      fixture bank of made-up questions.
    - **The live channel** is shaped like a Realtime broadcast on `run:<id>`. Wave 1 uses the Vite
      dev server's WebSocket.
11. **Verbs** are `lesson_draft`, `lesson_show`, `lesson_edit`, `lesson_check` and
    `question_search`, as Muse function tools.
    - A test reads `apps/cli/mcp-tools.json` and checks that names and required inputs match, so
      `jw mcp serve` and the hosted engine expose one tool set.
    - Each verb writes its effect as events.
12. **No route in wave 1.** A route brings a `ROUTES` entry, the `openapi.json` snapshot (a one-way
    door) and a terraform key.
    - The page drives `apps/web/dev/engine-plugin.ts`, which runs `acceptMessage` and `runStep`
      in-process on an `InMemoryStore`, beside `builder-plugin.ts`.
    - `vite.config.ts` loads it on `serve` only. Step 0 adds the line.
13. **PostHog's production failures are frozen tests,** written by the lead in step 0. Each is a
    scenario in `packages/jadwigo-ai/src/scenarios.test.ts` or a golden log in
    `packages/testing/src/runs/`:
    - a reload replays without a gap or a duplicate;
    - a follow-up sent mid-turn arrives once, after the turn;
    - a redelivered step pays once;
    - a stale attempt writes nothing;
    - a late event doesn't reopen an ended turn;
    - the budget steers at 50% and stops at 90%;
    - cancel during a verb stops before the next one;
    - the idle and max deadlines fire on their own clocks.
14. **Observability floor.**
    - The run id is the trace: every ledger row, log line and error event carries it.
    - The page's error row has "Copy details", which copies the run id and the attempt.
    - The stuck-run query waits for Postgres (wave 2).
15. **Workstreams.** The epic sits in the meta project. Each child carries one workstream label,
    the epic as its parent, and `wave:dl-z5ja-1` plus `lane:<x>`.
16. **Merging.**
    - Step 0 merges to `main` before any lane PR faces main.
    - A lane PR against the step-0 branch stays a draft with no `--auto` (`dl-5ssh.101`).
    - The lead's worktree is cut with `md delegate`, so `md merge-steward inbox --wait --epic dl-z5ja`
      works.
    - Hand-backs after the lanes stop go to the lead.

**Why the cut holds:**
- Step 0 writes every seam before a lane starts: the types, the stub signatures, the store's
  contract suite, the golden logs and the scenarios. The `dl-a38n` retro asked for exactly that.
- fold, store, verbs and web own disjoint folders.
- verbs and runner split `packages/jadwigo-ai/src` by folder. The runner calls verbs only through
  the step-0 `Verb` type and `MuseClient` interface, so it builds against `FakeMuse`'s stub before
  verbs lands.
- The web lane draws from the golden logs until the runner lands, and only then wires the plugin
  to `runStep`.
- No lane touches `packages/contracts`. A gap there is a message to the lead.

## Briefs

- A lane's brief is its issue:
  - scope and paths in `--description`;
  - the owner's words and the decisions in `--design`;
  - done-when as commands in `--acceptance`.
- The lead hands each lane its whole queue at once and waits for an acknowledgement.
- Each issue gets one PR, titled `<id>: <what>`. It stays a draft until `make check` is green, then
  goes `gh pr ready` and `gh pr merge --auto --squash` (once step 0 is on main).
- The lane notes on the issue what ran and what didn't. The steward closes the issue when the PR
  merges.
- A lane ends with `DONE`, `DONE_WITH_CONCERNS`, `NEEDS_DECISIONS` or `BLOCKED`, and its PR links.
