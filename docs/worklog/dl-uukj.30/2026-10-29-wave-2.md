# dl-uukj.30: wave 2 plan, the lesson overview

Epic `dl-uukj.30`. Wave label `wave:dl-uukj.30-2`. Wave 1 gave the parent one attempt at a time:
`/parent/attempts/<id>`, a tile per question, the review step with every try. Wave 2 puts every
attempt the pod reads of one assignment on one screen: a heatmap of attempts against questions,
a legend, a sheet per question, and a link from each cell into that attempt's own review. For a
family it is one row; for a tutor's pod it is one row per child.

- No XP or percentage for anyone (2026-10-18, 2026-10-03); the miss colour of 2026-10-24.
- Owner, 2026-10-29, this wave's planning: the unit of the overview is one assignment, its rows the
  attempts the caller's pod reads; a twin folds into its planned question's cell with a mark; the
  overview carries `attempt_result` rows only, so a try's value and the solution stay on the
  attempt's review page, and no key leaves the server (RULES.md rule 21).

Taken from Classtime's teacher heatmap: rows are the people, columns the questions, every cell
carries an icon as well as a colour, a column opens the question's answers. Added, since Classtime
lacks them: a count per column, a legend, time. Left out: points, sorting, hiding names, keyboard
stepping, tooltips (parents are on phones: the label is in the cell's accessible name).

## The screen

```text
Lekcja pytanie po pytaniu            Podejścia: 2   Zadane pytania: 12
                     1    2    3    4    5    6   …   12
 Ola         8/12    ✓    ✓    ◐    ✓    −    ↷        ✓
 Uczestnik 2 6/12    ✓    ◐ʹ   ✓    ·    ·    ·        ·      (still open)
 Od razu             2    1    1    1    0    0        1
 Legenda: ✓ Od razu  ◐ Po próbach lub z pomocą  − Jeszcze nie  ↷ Pominięte  … W trakcie  · Nie zadane  ʹ podobne pytanie
```

One cell's outcome, from a planned `attempt_result` row and the twins folded into it:

| outcome | rule | copy |
| --- | --- | --- |
| `first_try` | `ended = correct`, `first_try_correct`, `help_used = 0` | `parent_outcome_first_try` |
| `got_there` | `ended = correct` after more tries or help, or a folded twin ended `correct` | `parent_outcome_got_there` |
| `not_yet` | `ended = missed`; or `skipped` with a twin asked and none of them `correct` | `parent_outcome_not_yet` |
| `skipped` | `ended = skipped` and no twin asked | `parent_outcome_skipped` |
| `open` | the row is there and `ended` is null | `parent_outcome_open` |
| `not_asked` | no row for this column | `parent_outcome_not_asked` |

Columns are the planned rows across every attempt, keyed by `lesson_question_id` and ordered by
first `seq`: an assignment may span lesson versions, and the parent's pod cannot read the
version's list. A twin folds into the planned question it was added for, following `added_for`
to the planned root. A column header opens the question's sheet; a cell or a name goes to that
attempt's review page.

## Shared paths

- `packages/contracts`, `packages/api-client` and `packages/copy` change only in the lead's PR. A
  missing field or copy key is a message to the lead.
- Every lane PR targets `lead/dl-uukj.30-wave-2` until it merges, then GitHub retargets it to
  `main`. A stack updates by `git merge`, never by rebase. A lane PR waits for the retarget to
  `main` before auto-merge, so the steward reviews it once, on its own.
- The lead keeps `md merge-steward inbox --wait` and takes every hand-back once a lane stops.

## Stop rules for a lane

The repo's: the same step failed 3 times with no new information; "done when" needs a file the lane
does not own; a contract disagrees with the issue; a test the lane did not write fails; the next
step is a migration or a paid call. The stop note is 4 lines on the issue.
